# ADR-E006: Structured JSON Logging Standard

**Date:** 2026-08-06
**Status:** Accepted
**Decider:** JANUS Principal Architect
**Consulted:** ATLAS Chief Software Architect
**Services Impacted:** All
**Migration Lead Time Required:** Immediate
**Grace Period:** N/A

---

## Context

Multiple JANUS services produce logs. If each service uses a different log format, a unified log aggregation and search system cannot parse them consistently. Engineers debugging cross-service issues must learn multiple log formats and cannot write queries that span services. An incident that involves two JANUS services becomes twice as hard to diagnose if the logs from each service look different.

A standard log format is a prerequisite for ecosystem-level observability.

---

## Decision

All JANUS services emit logs as **structured JSON**, one JSON object per line, with the required fields defined in `standards/operations/logging-standard.md`.

**Required fields in every log entry:**
- `timestamp` — ISO 8601 UTC with millisecond precision
- `level` — one of `"error"`, `"warn"`, `"info"`, `"debug"`
- `message` — human-readable description
- `service` — the service name (lowercase: `"atlas"`, `"venus"`)
- `requestId` — UUID of the current request, for correlation

---

## Rationale

**Structured JSON** because:
- Machine-parseable — log aggregation systems (Datadog, Grafana Loki, Elasticsearch, etc.) can parse structured JSON without per-service parsing rules
- Human-readable — JSON is reasonably readable in a terminal for development
- Extensible — additional fields can be added to any log entry without changing the format
- Filterable — structured fields can be indexed and queried efficiently

**Required fields** because:
- `timestamp` — logs without timestamps are impossible to correlate with events
- `level` — filtering by severity is the most common log query
- `message` — human-readable summary for engineers who encounter the log entry
- `service` — in an aggregated log view spanning multiple services, the service name must be immediately identifiable
- `requestId` — cross-service correlation requires a shared identifier that propagates through the call chain

---

## Consequences

**Positive:**
- A single log aggregation configuration ingests all JANUS service logs
- Cross-service traces are possible by filtering on `requestId`
- Engineers working across services encounter the same log structure everywhere

**Negative / Trade-offs:**
- Services cannot use `console.log` for production logging (which produces plain text, not JSON)
- Each service must integrate a structured logging library

**Implementation:**
Each service chooses its structured logging library via service-level ADR. The library must produce JSON output with at minimum the five required fields. Popular options: `pino` (Node.js), `winston` (Node.js), native `console.log` replacement with JSON formatting.

**The `service` field value** is registered in `services/registry.yaml` to ensure consistent naming across all JANUS services. The field value is the service's lowercase codename: `atlas`, `venus`, `narcos`, etc.

**The `requestId` propagation contract** is:
- Generated by the service's inbound handler on first contact
- Returned to the caller in `X-Request-ID` response header
- Sent to downstream JANUS services in `X-Request-ID` request header
- Included in every log entry produced during that request's lifecycle
